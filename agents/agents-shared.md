# Shared agent instructions

## Agent instructions file structure

All of the following are user-scoped.

- `~/.agents/agents-shared.md`: shared instructions for all agents on all
  computers.
- `~/.agents/agents-shared.extra.md`: machine-specific instructions for all
  agents. Not committed to public git; suitable for company-internal details.
- `~/.agents/AGENTS.md`: instructions for all agents. Generated by
  `make -C ~/.agents` from `agents-shared.md` and `agents-shared.extra.md`.
- `~/.claude/CLAUDE.md`: instructions for Claude only. Includes
  `AGENTS.md` and `CLAUDE.extra.md`.
- `~/.claude/CLAUDE.extra.md`: machine-specific instructions for Claude only.
  Not committed to public git.

After editing `agents-shared.md` or `agents-shared.extra.md`, run
`make -C ~/.agents`. It regenerates `AGENTS.md`. Vim does this on save via
`~/.agents/.lvimrc`; approve loading it outside the sandbox when prompted.

## Design docs and plans

Agent-generated design docs, specs, and implementation plans go in
`~/.agents/specs/`, named `YYYY-MM-DD-<topic>-design.md` or
`-plan.md`. That directory is a git repo with no remote; commit specs there.
This overrides any skill's default location, including the
Superpowers brainstorming and writing-plans skills, which default to
`docs/superpowers/specs/` inside the working repo.

They do not belong in the repo being worked on. A project repo holds code and
the documentation its readers need; a spec written to reach one commit is
neither, and in repos that publish `docs/` it would ship to the docs site
alongside real contributor documentation.

## Style

Avoid spurious "add-one-to-i" comments. Like this:

```c
// Increment i by 1
i++;
```

Reading the code should explain the code.

Comments carry constraints and facts. Rationale, alternatives considered, and
"why not X" belong in the commit message or the README, not next to the code.
A comment that argues for the design is in the wrong place.

Length follows from that, so don't optimize for short. An external constraint
worth four lines gets four lines — APCA contrast thresholds, an upstream bug, a
wire format. A design you'd like me to agree with gets zero.

Specifically, cut:

- Meta-commentary on the comment itself ("Scope: this only checks...", "see
  file header").
- Emphasis used to persuade: `*deliberately*`, `NOT`, **bold**.
- Parenthetical asides about adjacent findings. Those go in the ticket.
- Docblocks on local helpers whose signature already says it.
- Hedges and qualifiers that add no fact.

Prefer stating the mechanism plainly: "templated values can't be checked
statically and are skipped" over a paragraph establishing why that was the
right call.

## Reviews

Match the bar I apply in review: no unused vars/params/config, no speculative abstraction, simplest thing that works, idiomatic for the language. I question necessity hard — if you're adding something, be ready to say why it's needed, or don't add it.

## Uncertainty

Never fill gaps with confident guesses. "I don't know" and hedged findings are
welcome; a claim stated flatly is read as verified.

## Problems With Tools

Sometimes we land on an inelegant solution or workaround because a tool is
broken/insufficiently general/etc. This is a signal! Before proposing a
workaround for a tool's behavior (unsetting what it sets, wrapping it, patching
around it), do these steps.

- Ensure we're on the latest version. If not, upgrade and retry.
- Search for github issues - open or closed. See if anyone has a better
  workaround.
  - Search by the exact identifier (env var, flag, function name, error text) in the tool's repo
  - If two tools interact, search both
- Report what you searched and what you found, with links, before settling on the workaround

## Git hooks

`core.hooksPath` is set globally to `~/.config/git/hooks`, but that hook is a
dispatcher, not a replacement: it runs `.git/hooks/<name>` and `.husky/<name>`
first, then global pre-commit, then the repo's `.pre-commit-config.yaml`. So a
repo-local `.git/hooks/pre-commit` **is** live — don't conclude it's dead just
because `core.hooksPath` points elsewhere.

Never set `core.hooksPath` to test a hook: worktrees share `.git/config`, so
`git -C <worktree> config` writes to the parent repo. Use `git -c
core.hooksPath=... commit` instead, which can't persist.

## `update.d` scripts

Many tools require updating - brew packages, vim plugins, fish plugins - the
list goes on. Our user-level pattern for this is for each box to have a
`~/.local/share/update.d` directory with scripts that update all its tools. Each
script is idempotent and non-interactive. Where possible, each tool's
auto-update is disabled. The scripts are run as a group by a human executing the
`update-system` command, which auto-discovers scripts. (Additionally, the main
box may ssh into other boxes and run `update-system` there too.)

When adding a new tool, piece of config, etc - consider its update mechanism.

- If it has a built-in auto-update, generally you should disable it.
- If it's already covered by an existing `update.d` script, you're done (e.g.
  brew installed packages are definitely fine.)
- If it has a NEW update mechanism (maybe a file needs to be curled to a
  location, maybe it needs a cache refresh or a special command run), add a new
  script to `~/.local/share/update.d`.

## Global installs

1. Prefer brew installs where possible
2. For python, append to `~/.config/python/global-requirements.txt` and run
   `~/.local/share/update.d/python-global-deps.sh`
3. For js, append to `~/.config/js-global-deps.txt` and run
   `~/.local/share/update.d/js-global-deps.sh`

## Fish config file structure

In general, fish config goes in ~/.config/fish/conf.d/XX_name.fish.
If it's machine-specific, i.e. work or home machine only, it goes in
~/.extra.fish.
